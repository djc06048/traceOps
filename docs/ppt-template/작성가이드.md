# 성과 제출용 HTML 슬라이드 작성 가이드 (v3)

> 용도: HTML로 슬라이드를 만들고 PDF로 저장해 한 장씩 넘겨 보는 한화시스템 내부 보고 자료의 작성 기준.
> 한화시스템 템플릿에서는 **색상 팔레트와 로고만** 가져온다. 레이아웃, 도형, 배치는 이 문서의 기준으로 새로 설계했다.
> 예외: **표지, 목차, 엔딩**은 템플릿 형태(주황 바탕 + 링 아트)를 유지한다.
> 내용 출처: `docs/제안서_추진현황_요약.md`, 실제 구현 화면. 생성 코드는 `tools/build_prowin.py`, `tools/prowin.css`.

---

## 1. 설계 원칙

1. **한 장 한 메시지.** 모든 본문 장은 `제목 → 거버닝 메시지(제목 바로 아래) → 근거 그림·도형` 순서로 읽힌다.
2. **증거는 실제 화면.** 기능 설명은 캡처와 확대 이미지로 보여 준다.
3. **여백과 면으로 구분한다.** 테두리 박스, 헤더 띠, 장식 도형 대신 옅은 면, 간격, 글자 크기로 위계를 만든다.
4. **강조색은 한 가지 의미에만.** 주황은 핵심 강조, 갈색·탄·회색은 보조.
5. **번호는 원 안의 숫자(①, 동그라미)를 쓰지 않는다.** 큰 숫자 글자(`01`), `STEP 01` 라벨, 둥근 사각 태그를 쓴다.
6. **빈 곳을 남기지 않는다.** 상세 장은 `확대 + 설명 + 핵심 포인트 + 기대 효과`까지 채운다.
7. **약점은 싣지 않는다.** 한계와 미구현은 `향후 계획`에 고도화 과제로만 쓰고, 상세 보완 목록은 개발자용 문서(`ProWin_화면보완사항.md`)에 둔다.

## 2. 페이지 규격과 글꼴

A4 가로(11.69×8.27in), 좌표는 inch 절대값. 좌우 여백 0.70, 콘텐츠 폭 10.29.

```css
@page { size: 297mm 210mm; margin: 0; }
.slide { position:relative; width:11.69in; height:8.27in; overflow:hidden; page-break-after:always; }
@media print { * { -webkit-print-color-adjust:exact; print-color-adjust:exact; } }
```

**글꼴은 저장소의 `docs/nanum-barun-gothic/` 를 `@font-face` 로 불러 쓴다.** (Regular 400, Bold 700, Light 300)

```css
@font-face{ font-family:'NanumBarunGothic'; font-weight:400; src:url('../nanum-barun-gothic/NanumBarunGothic.ttf'); }
@font-face{ font-family:'NanumBarunGothic'; font-weight:700; src:url('../nanum-barun-gothic/NanumBarunGothicBold.ttf'); }
@font-face{ font-family:'NanumBarunGothic'; font-weight:300; src:url('../nanum-barun-gothic/NanumBarunGothicLight.ttf'); }
```
HTML 위치가 바뀌면 상대 경로도 함께 바꾼다. PDF 변환 전에 `document.fonts.ready` 를 기다린다.

| 용도 | 크기 | 굵기 |
|------|------|------|
| 페이지 제목 | 26pt | Bold |
| 거버닝 메시지 | 14pt, 행간 1.6 | Regular, 핵심어만 Bold |
| 카드 제목·키워드 | 16~22pt | Bold |
| 본문 | 12.5~14pt | Regular |
| 보조·캡션·태그 | 10~12pt | Regular/Bold |

## 3. 색상 (템플릿에서 가져온 값만)

```css
:root{ --orange:#F46A25; --orange-2:#F8931F; --orange-bg:#FFF0E6; --brown:#6E5744; --tan:#AF947E;
       --sand:#F3ECE5; --gray-bg:#F7F5F3; --line:#E5E0DB; --text:#2F2F2F; --sub:#6B6B6B; }
```
사용 비율은 흰 바탕 70%, 옅은 면 20%, 주황 5~8%, 갈색 3~5%. 팔레트 밖 색은 쓰지 않는다.

## 4. 공통 틀 (표지·목차·엔딩 제외)

```
y 0.55  [배지]  페이지 제목 (26pt Bold)                          [칩]
y 1.18  거버닝 메시지 1~2줄 (14pt, 핵심어 Bold + 연한 주황 밑줄 강조)
y 2.00  ──────────── 콘텐츠 영역 (~7.45) ────────────
y 7.78  [한화시스템 로고]                                        쪽번호
```

- **배지**: 주황 둥근 사각(0.78×0.36in), 흰 글자 12pt Bold. 장 구분(`개요`, `구현`, `계획`).
- **칩**: 우측 상단 회색 알약(1.8×0.34in), 10.5pt. 이 장의 보조 분류(`핵심 기능 1/4`, `시스템 구성` 등).
- **거버닝 메시지**: 첫 줄은 결론(핵심어 `<b>`), 둘째 줄은 근거 한 줄. 아래 6장 작성 규칙을 따른다.
- 저작권 문구, 구분선, 한화시스템 템플릿 헤더는 쓰지 않는다.

## 5. 슬라이드 패턴

| 코드 | 이름 | 용도 | 핵심 구성 |
|------|------|------|----------|
| P1 | 원칙 카드 3열 | 소개 | 선 아이콘 + 제목 + 설명 3줄, 하단 갈색 결과 바 |
| P2 | 문제 4열 + 시사점 | 추진 배경 | 큰 연번 `01`, 카드 4개, 하단 갈색 시사점 3열 |
| P3 | 번호 행 3줄 | 목표 | 큰 숫자 `01` + 세로선 + 제목·설명 + 우측 주황 알약 결과 |
| P4 | 전후 비교 | 기대효과 | 항목명 / 도입 전(회색) / 삼각 화살표 / 도입 후(주황 면 + 좌측 선) |
| P5 | 역할별 프로세스 | 업무 흐름 | 4열: 상단 색 막대 + `STEP 01` + 단계명 + 역할 알약 + 카드 + 관련 화면, 하단 결과 바 |
| P6 | 화면 상세 | 주요 기능 | 좌: 전체 캡처 + 번호 강조 박스, 우: 확대 카드 2개 + 설명, 하단: 핵심 포인트 + 기대 효과 |
| P7 | 타일 갤러리 | 부가 기능 | 4×2 또는 3×2 이미지 타일 + 이름 + 한 줄 설명 |
| P8 | 구조도 + 기술 칩 | 기술 구성 | 3블록(브라우저, 서버, 저장소) + 화살표 + 기술 스택 칩 + 결과 바 |
| P9 | 로드맵 | 향후 계획 | 좌: 고도화 과제 목록, 우: 큰 숫자 `01`~`03` 세로 단계 + 결과 바 |

### P6 화면 상세 (핵심 패턴) 규격
- 좌측 전체 캡처: x 0.70, y 2.10, 폭 5.0. 캡처 위에 **주황 실선 강조 박스**(2px, 모서리 0.04in)와 **둥근 사각 번호 태그**.
- 우측 확대 카드: x 6.35, 폭 4.64, 높이 최대 1.05in. 카드 위에 `번호 태그 + 제목(14pt Bold)`, 아래에 설명 1~2줄(12pt).
- 강조 박스와 확대 카드는 **옅은 주황 음영(10%) + 점선**으로 이어 확대되는 느낌을 준다. 이미지는 따로 자르지 않고 같은 PNG를 CSS `background-position` 으로 잘라 쓴다. 강조 박스 좌표 = 확대 영역 좌표(원본 px).
- 캡처 아래 `화면 위치  제안 워크스페이스 > ○○` 한 줄.
- 하단(y 6.5): 좌 `핵심 포인트`(`›` 불릿 2개), 우 `기대 효과`(`--sand` 면 + 주황 좌측 선 + 14pt Bold 한 줄).
- 확대 영역은 폭:높이 약 4.4:1(440×100 css px 안팎)로 잡아 글자가 읽히게 한다.

## 6. 거버닝 메시지 작성 규칙

- 위치는 **제목 바로 아래 1~2줄**. 첫 줄은 결론, 둘째 줄은 근거나 범위.
- **핵심어는 `<b>`로 감싼다**(연한 주황 밑줄이 자동 적용). 한 줄에 1~2개까지.
- 합니다체로 간결하게 쓴다. 대시(—), 화살표(→), 물음표, 느낌표, 슬래시 나열, 과장 수식어를 쓰지 않는다.
- 누가, 무엇을, 어떻게 바뀌는지를 쓴다. 문서에 없는 수치와 효과는 쓰지 않는다.

| 나쁜 예 | 좋은 예 |
|--------|--------|
| RFP·요구사항 관리 — 모든 제안 작업의 출발점 | RFP와 **요구사항을 한 화면에서 정리**하여 제안 작업의 기준으로 삼습니다. |
| 제안서 검토 화면입니다 | 슬라이드를 보며 **참여 인원 전원이 의견을 남기고** 결정 근거를 기록합니다. |
| 표준화로 경쟁력을 극대화한다 | 제안 수행이 **개인 의존에서 표준 절차와 축적 자산 기반**으로 바뀝니다. |

## 7. 표지·목차·엔딩

- **표지**: 상단 5.0in 주황 바탕(`assets/bg-title-art.jpg`), 좌상단 흰 탭 로고, 영문 부제 24pt Light, 제목 40pt Bold 흰색, 하단에 참여자. **날짜는 넣지 않는다.**
- **목차**: 회색 바탕(`bg-contents-art.jpg`), `CONTENTS` 40pt, 파트별 주황 띠 + 번호 항목.
- **엔딩**: 주황 바탕 전체, 중앙 흰 박스 `End of document / 감사합니다`.

## 8. 콘텐츠 규칙

1. 사실은 `제안서_추진현황_요약.md`와 실제 화면에서만 가져온다. 정량 효과 문구를 만들지 않는다.
2. 상반기 성과는 `설계 완료`, `프로토타입 구현`, `사전 검증`으로 정확히 표현한다.
3. 아직 동작하지 않는 기능(요구사항 자동 추출, 유사 사례 추천)이 흐름에 들어가면 작은 `고도화` 태그를 단다.
4. 고객사 로고 박스, 날짜, 담당자명은 넣지 않는다. 참여자는 표지에 이름만.
5. 참고용 외부 레이아웃 이미지는 저장소에 커밋하지 않는다.

## 9. PDF 저장

```bash
node -e "
const { chromium } = require('playwright');
(async () => {
  const b = await chromium.launch(); const p = await b.newPage();
  await p.goto('file://' + process.argv[1]);
  await p.evaluate(() => document.fonts.ready);
  await p.pdf({ path: process.argv[2], preferCSSPageSize: true, printBackground: true });
  await b.close();
})();" /절대경로/성과제출_ProWin.html /절대경로/성과제출_ProWin.pdf
```
저장 후 확인: 페이지 수 = 슬라이드 수, `pdffonts` 에 NanumBarunGothic 포함, 글자 잘림 없음, 마지막 장 뒤 빈 페이지 없음.

## 10. 점검표

- [ ] 제목 바로 아래에 거버닝 메시지 1~2줄, 핵심어 `<b>`
- [ ] 메시지에 대시, 화살표, 물음표 없음
- [ ] 동그라미 번호 없음(큰 숫자, STEP 라벨, 둥근 사각 태그 사용)
- [ ] 글꼴이 NanumBarunGothic 로 로드됨
- [ ] 패턴 P1~P9 중 하나만 사용, 빈 영역 없음
- [ ] 강조색 한 가지 의미, 팔레트 밖 색 없음
- [ ] 캡처 번호와 설명 번호가 1:1 대응
- [ ] 문서에 없는 수치·효과 없음, 약점 문구 없음, 날짜 없음
