# TraceOps · ReqSync 보완 및 고도화 정리 (개발자 전달용)

> 대상: `traceops-simple` (Python 표준 라이브러리 서버 + SQLite, 바닐라 JS). `main` 브랜치 소스를 직접 실행하고 코드를 읽어 정리했다.
> 성과 보고 자료에는 `고도화 계획`으로만 표현한다. **구현 방안은 TraceOps 담당 개발자가 작성한다.** 이 문서는 무엇이 비어 있는지, 왜 필요한지, 확인할 기준이 무엇인지를 정리한 것이다.
> 구성: **우선순위(P0 → P2) 순서**. 주요 기능 완성이 최우선이며, TraceOps는 **로컬 LLM 추출(ReqSync)** 과 **연계관리 보완**이 먼저다.

> **최신화 내역** (장표 21장 기준): ① 수행주기(착수 → 기술협상 → 분석 → 설계 → 개발·단위 → 통합) 기준으로 장표 흐름 정리 ② 연계관리를 "기간계 메인 프로세스 + 채널 + AI Agent 연계, 누락 방지, 통합테스트 대상 파악"으로 정리 ③ 우선순위 순서로 재정렬(주요 기능 → 증적·문구 → 소스 보완 → 고도화 → 상용화) ④ 단계말 스냅샷, 확정 후 수정 검토, 엑셀·PMS 연동은 6장 고도화

## 수행주기와 보완 항목 대응

| 수행주기 | TraceOps · ReqSync 적용 | 관련 보완 항목 |
|----------|------------------------|----------------|
| 착수 | 현황 엑셀·PMS 데이터 연동 | 6장 엑셀·PMS 연동 |
| 기술협상(요구사항 상세화) ~ 분석 | **ReqSync**: 회의록으로 요구사항 보완·확정, 증적 이력 | 1장 로컬 LLM 추출, 4장 증적·문구 |
| 설계 | **연계관리**: PL이 프로세스(채널 → 기간계 → AI Agent 포함)를 설계 | 2장 호출구조 통합, 3장 A2·A4·A8 |
| 개발·단위테스트 | 개발 항목으로 개발자별 배분 | 3장 A4·A7 |
| 통합테스트 | 프로세스 전체 동작 확인 | 3장 A3 |
| 전 구간 | 요구사항~테스트 정합성, 누락 방지 안내 | 3장 A5·A6, 6장 스냅샷·확정 후 수정 검토 |

## 0. 한눈에 보기 (우선순위 순)

| 순위 | 장 | 항목 | 우선순위 | 현재 상태 |
|------|----|------|----------|-----------|
| 1 | 1장 | **로컬 LLM 결정사항 추출 연동** (ReqSync 핵심) | **P0** | 사전 분석 결과를 API로 조회. 실행 연동 없음 |
| 2 | 2장 | **호출구조 정적분석 POC TraceOps 통합** (연계관리 핵심) | **P0** | POC 결과 데이터만 시드로 존재. 소스 코드는 저장소에 없음 |
| 3 | 3장 | **연계관리 보완**: 메서드·요구사항 단위 누락 검증, 프로세스–통합테스트 연결, 채널·AI Agent 노드 | **P0** | 프로세스–통합테스트 미연결, 요구사항 단위 누락 경고 없음 |
| 4 | 4장 | ReqSync 증적·문구 (안내 문구 불일치는 P0) | P0~P1 | 증적 내보내기 없음, 문구 불일치 |
| 5 | 5장 | 소스 기준 보완 (인증·확정자 연동, 동시 편집, 테스트) | P1 | 5-1 표 |
| 6 | 6장 | 고도화 (단계말 스냅샷, 확정 후 수정 검토, 제출 산출물, 엑셀·PMS 연동, 채널·AI 확장 등) | P1~P2 | 미착수 |
| 7 | 7장 | 상용화 대비 | P2 | 7장 표 |

우선순위: P0 = 제출·시연 전 반드시, P1 = 고도화 착수 전, P2 = 고도화와 함께.

## 1. 로컬 LLM 결정사항 추출 (ReqSync) (P0)

### 1-1. 현재 상태 (소스 근거)
| 항목 | 현재 구현 | 근거 |
|------|-----------|------|
| 회의록 업로드 | 파일명으로 등록된 회의(`meetings` 12건)와 매칭만 함. 파일 내용은 읽지 않음 | `requirements-review.js` `handleUpload` |
| 결정사항 데이터 | 사전 분석된 8건(확정 3, 검토 1, 미결 4)을 `decisions` 테이블에 시드로 저장. 6개 회의에만 존재 | `data/decisions.json`, `reqdb.py` |
| 분석 중 표시 | "회의록 원문을 읽는 중... / 결정사항 추출 중... / 요구사항 목록과 매칭하는 중..." 문구를 **연출**로 순환 표시 | `runLoading`, `LOAD_STEPS_FRESH` |
| 조회 | `GET /api/decisions`, `GET /api/meetings`, `GET /api/reviews` 로 읽기만 함 | `server.py` |
| 검토·확정 | PL이 편집 후 확정하면 `PUT /api/reviews/{id}` 로 저장하고 요구사항 내역과 변경 이력에 반영 | `persistReview`, `reqdb.py` |

**정리**: 추출·매칭·개정안은 **이미 만들어진 결과를 보여 주는 단계**이고 AI 실행은 없다. 검토·확정·이력 부분은 실제로 동작한다.

### 1-2. 목표
회의록(.txt) 업로드 → **서버 내 로컬 LLM**이 결정사항·미정사항을 추출 → 요구사항과 매칭하고 개정안 생성 → 기존 검토 화면에서 PL이 확정. 외부 전송 없이 사내망에서 동작해야 한다.

### 1-3. 개발자가 정할 사항 (구현 방안은 개발자 작성)
- 모델과 실행 방식(예: 사내 반입 가능한 오픈 모델, 실행 런타임, GPU/CPU 사양)
- 긴 회의록(재생시간 31~119분 분량) 처리 방식(청크 분할, 요약, 중복 병합)
- 프롬프트와 출력 형식(결정사항 JSON), 오류 시 재시도, 시간 제한
- 작업 실행 구조(동기/비동기 작업, 진행률 표시를 실제 진행과 연결)

### 1-4. 연동 지점 (현재 구조에서 필요한 변경)
| 항목 | 내용 |
|------|------|
| 업로드 API | 현재 없음. 파일 업로드 엔드포인트와 `meetings` 신규 등록이 필요(현재는 등록된 파일명만 허용) |
| 추출 작업 | 업로드 후 작업 ID를 만들고 진행 상태를 조회. 완료 시 `decisions` 테이블에 저장 |
| 결과 스키마 | 기존 `decisions` 컬럼을 그대로 채운다: `meeting_file`, `excerpt_ts`, `excerpt`(발언 원문), `decision`, `raw_status`, `final_status`, `verification_note`, `req_id`, `confidence`, `addition`, `replace_with`, `new_req_hint` |
| 2차 검증 | 화면에 "1차 생성 → 2차 검증"이 이미 표기됨. 2차 검증(원문 근거 일치 확인)의 실제 로직이 필요 |
| 화면 | 로딩 연출 대신 실제 진행 표시. 실패·시간 초과 표시 |

### 1-5. 원칙 (변경 금지)
- **AI는 추출과 제안까지, 반영 확정은 PL**. 확정 전에는 요구사항 내용이 바뀌지 않는다.
- 모든 반영은 근거 회의와 결정사항 ID와 함께 변경 이력에 남긴다(현재 구현된 동작).
- 발언 원문(`excerpt`)과 시각(`excerpt_ts`)을 반드시 함께 저장한다. 원문에서 근거를 찾지 못한 결정사항은 저장하지 않는다.

### 1-6. 평가와 수용 기준
- **정답셋**: 현재 사전 분석된 결정사항 8건과 회의록 원문(원문 파일은 저장소에 없고 로컬에만 있음)을 정답으로 사용.
- **지표**: 결정사항 재현율·정밀도, 요구사항 매칭 정확도, 원문 근거 일치율, 처리 시간.
- **수용 기준**: 샘플 회의록 6건 이상에서 정답셋 대비 지표를 측정하고, 목표 수치는 측정 후 합의한다. 실패 시 사용자가 알 수 있어야 한다.

### 1-7. 확인 필요
- 회의록 원문에 실명과 고객 업무 논의가 포함되어 있다. 저장 위치와 보관 기간 정책이 필요하다. 현재 저장소는 원문을 제외(`.gitignore`의 `ai/sample/`)하고 있다.
- 하드코딩된 PL 이름 (`requirements-review.js`의 `PL_NAME`)을 로그인 사용자로 대체해야 확정자 기록이 의미를 가진다.

## 2. 호출구조 정적분석 POC의 TraceOps 통합 (P0)

### 2-1. 현재 상태
- POC는 구현되어 있고 그 결과로 연계 데이터를 추출했다. **다만 분석 코드는 이 저장소에 없다.** 삭제된 스캐폴딩 커밋(`00174b5` 이전)의 `analyzer/README.md`는 자리만 잡은 상태였다.
- TraceOps에는 **추출 결과가 시드 JSON으로만** 들어 있다: `data/linkage_transactions.json` (트랜잭션 3건, 호출 노드 11개, 매핑 3건).
  - 트랜잭션 예: `TX_QPM_ACMLM1`(누적위험 한도확인), 호출 노드 예: `FcdLtrUtgu#executeacmLmAplCpltImprChek`(클래스#메서드).
- 연계 캔버스는 AS-IS 콜트리를 읽어 노드에 매핑하는 화면(`linkage.html`, `lk_transaction`, `lk_call_node`, `lk_mapping` 테이블)까지 구현되어 있다.

### 2-2. 보완 목표
분석기를 TraceOps 안으로 편입하여 **소스 → 호출구조 추출 → `lk_transaction`/`lk_call_node` 자동 적재 → 연계 캔버스 매핑**이 한 흐름으로 이어지게 한다.

### 2-3. 개발자가 정할 사항
- POC 코드의 위치와 이관 방식(저장소 편입 여부), 분석 대상 언어·프레임워크 범위
- 실행 방식(수동 실행 / 화면에서 실행 / 정기 실행)과 결과 갱신 방식(재분석 시 기존 매핑 유지)
- 트랜잭션 식별 규칙(`TX_QPM_*` 부여 방식), 호출 노드 순서·부모 관계(`parentId`, `order`) 산정 방식

### 2-4. 통합 시 지켜야 할 점
- 사람이 만든 매핑(`lk_mapping`)과 TO-BE 설계는 재분석으로 덮어쓰지 않는다. 자동 생성분과 수동 수정분을 구분하는 상태 값이 필요하다. 삭제된 스캐폴딩의 설계에도 `edit_state(AUTO/MANUAL)` 개념이 있었다.
- AS-IS 프로세스는 조회 전용이라는 현재 규칙을 유지한다.
- 시스템 식별자(클래스·메서드명)는 그대로 노출된다. 외부 공유 시 노출 범위를 확인한다.

### 2-5. 수용 기준
- 샘플 소스에서 추출한 결과가 현재 시드(3건, 11개, 3건)와 동일하게 재현된다.
- 재분석 후에도 수동 매핑이 유지된다.
- 추출 실패·부분 실패가 화면에 표시된다.

## 3. 연계관리 보완: 누락 방지, 통합테스트, 채널·AI Agent (P0)

장표의 취지는 **프로세스 안의 메서드 하나만 빠져도 프로세스가 동작하지 않으므로, 프로세스 전체를 분석·설계·개발·통합테스트까지 관리**하는 것이다. 현재 구현과의 차이는 다음과 같다.

| # | 구분 | 현재 | 부족한 점 / 보완 요청 | 우선 |
|---|------|------|----------------------|------|
| A1 | 빠진 메서드 확인 | 목록에는 매핑 건수와 `TO-BE 없음` 표시만 있음 (`lk_processes`). 장표에서는 사용하지 않는 표기 | **어떤 메서드가 개발 대상에서 빠졌는지** 구체적으로 보여 주는 화면(메서드, 연결된 개발 항목, 담당 개발자) | P1 |
| A2 | 메서드 ↔ 개발 항목 | 콜트리 메서드는 캔버스 노드에 매핑되고, 개발 항목 기반 캔버스는 `N / M 개발완료`를 계산 | 메서드가 **분석·설계·개발 항목 어디에도 연결되지 않은 경우**를 검증하는 규칙이 없음 | **P0** |
| A3 | 프로세스 ↔ 통합테스트 | 연계 테이블(`lk_*`)과 통합테스트(`integration_items`)에 **연결이 없음** (코드 검색 결과 참조 없음) | 프로세스(트랜잭션) 단위로 통합테스트를 연결하고, 프로세스의 모든 메서드가 포함되는지, 통합테스트가 PASS인지 확인 | **P0** |
| A4 | 담당자 | 노드에 담당자 개념이 없음. 프로세스 `owner`만 있음 | 메서드(개발 항목)별 담당자를 프로세스 화면에서 함께 확인 | P1 |
| A5 | 요구사항 단위 누락 | 하위 연결이 없으면 설계·개발·단위 행에 `하위 ○○ 미등록`을 표시하고, 삭제·변경 시 영향 팝업과 삭제 차단이 있음 | **요구사항 기준**으로 매핑 현황(분석·설계·개발·테스트에 연결됐는지)과 어디에도 매핑되지 않은 요구사항 목록이 없음. 개발 항목을 지워 요구사항이 고아가 되어도 요구사항 화면은 경고하지 않음 | **P0** |
| A8 | 채널·AI Agent 연계 | 노드 성격은 `서비스`, `인터페이스(대외계 연결)`, `인터페이스(채널계 연결)` 3종(`NODE_CATEGORY_LABEL`) | 채널 종류(CM, TM, 콜센터)와 **AI Agent**를 노드 유형으로 추가하고, 채널 요청 → 기간계 메서드 → 응답, 프론트 액션 → 기간계 Input 생성(조회 단계들) → AI Agent의 호출 경로를 한 캔버스에서 관리. AI Agent가 호출하는 기간계 메서드가 개발 대상에서 빠지지 않았는지 확인 | P1 |
| A7 | 사용자와 배분 | 연계관리는 PL(메인 설계자)이 사용하고 작업자 모드는 조회만 가능. 개발 항목 기반 캔버스의 노드는 개발 항목을 참조하므로 개발자 배분은 개발 항목의 `작업자`로 이루어짐 | 캔버스 노드에 담당 개발자 표시와 개발자별 필터, 미배정 노드 경고 | P1 |
| A6 | 저장 전 확인 | 변경 영향 팝업은 단계별 항목 화면에 있음 | 저장 시점에 "매핑이 끊기는 요구사항 N건"을 요약해 경고하고 사용자가 확인 후 진행 | P1 |

단계말 스냅샷과 제출 산출물 활용(요구사항~테스트 정합성 기준의 확정본 저장과 산출물 생성)은 6장 고도화 항목이며, 현재는 `내보내기`(JSON) 수준이다.

수용 기준(예): ① 개발 항목 삭제 시 매핑이 끊기는 요구사항이 즉시 안내된다. ② 요구사항 화면에서 "미매핑 요구사항" 필터와 개수가 보인다. ③ 프로세스를 열면 통합테스트 연결과 결과가 함께 보이고, 메서드 누락이 있으면 통합테스트 PASS여도 경고한다.

## 6. 고도화 (P1~P2)

프로젝트 수행주기(착수 → 기술협상(요구사항 상세화) → 분석 → 설계 → 개발·단위테스트 → 통합테스트) 기준으로 필요한 고도화 항목이다.

| 항목 | 목표 | 현재 |
|------|------|------|
| **단계말 산출물 스냅샷 확정** | 분석, 설계, 개발·단위, 통합 단계가 끝날 때 해당 단계 산출물을 변경 불가한 스냅샷으로 확정하고 이력 보관 | 없음. `내보내기`(JSON)만 있음 |
| **확정 후 수정 시 품질 검토** | 스냅샷 확정 이후 산출물을 수정하려면 변경 사유 입력, 검토자 검토·승인, 재확정을 거치고 이력을 남김. 하위 단계에 재검증 표시 | 재검증 표시(상위 변경 시 하위에 표시)는 있으나 확정·승인 절차 없음 |
| **제출 산출물 활용** | 요구사항~테스트 정합성 기준으로 단계별 제출 산출물(목록, 매핑표)을 생성 | 없음 |
| **기존 엑셀·PMS 데이터 연동** | 현재 엑셀과 PMS로 나뉘어 있는 요구사항·단계별 항목을 가져오기(양식 정의, 검증 결과 리포트)와 내보내기로 연결하고, 가져온 뒤 정합성 오류를 일괄 표시 | 없음. 시드 JSON과 내보내기만 있음 |
| 채널·AI Agent 연계 확장 | 채널(CM, TM, 콜센터)과 AI Agent를 노드로 구분하고 호출 경로를 추적 (예: 콜센터 설계 목록 조회, AI 인수지침 위배해소 Agent) | 노드 성격 3종만 있음 (3장 A8) |
| 연계 기반 우선순위 수립 | 연계 관계를 기준으로 개발 우선순위를 자동 제안 | 없음 |
| 변경 영향 추적 | 요구사항 변경 시 영향받는 분석·설계·개발·테스트·연계 항목 추적, 누락 사전 차단. 현재 연결 변경·삭제 시 영향 팝업이 있으며 연계까지 확장 | 단계별 항목까지 |
| 수행관리 자동화 | 진척 모니터링, 통합테스트 시나리오 자동 구성 | 없음 |

## 7. 상용화 대비 (P2)
| 영역 | 보완 방향 |

## 8. 권장 진행 순서
1. **P0 (주요 기능 완성)**: 1장 로컬 LLM 추출 연동 → 2장 호출구조 분석 통합 → 3장 A2(메서드 연결 검증)·A3(프로세스–통합테스트 연결)·A5(요구사항 단위 누락 경고) → 4장 B3(안내 문구). 구현 방안 작성부터 시작
2. **P1**: 3장 A1·A4·A6·A7·A8(채널·AI Agent 노드), 4장 B1(증적 내보내기), 5장(인증·확정자 연동, 오류·로그, 동시 편집, 테스트), 6장 단계말 스냅샷·확정 후 수정 검토
3. **P2**: 6장 나머지(제출 산출물, 엑셀·PMS 연동, 변경 영향 추적, 수행관리 자동화), 7장 상용화 대비
