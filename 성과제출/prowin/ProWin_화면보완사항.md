# ProWin 보완 및 고도화 정리 (개발자 전달용)

> 대상: `ProWin/backend` (Spring Boot 3.3.5 · Java 17 · SQLite · Apache POI 5.3.0), `main` 브랜치 소스.
> 근거: 백엔드를 로컬에서 직접 빌드·기동하여 샘플 PPT와 한화시스템 템플릿 PPT(29장)를 업로드하고, 합본을 생성해 결과를 열어 확인했다.
> 성과 보고 자료에는 싣지 않는다. 보고 자료에는 `고도화 계획`으로만 표현한다.
> 구성: **우선순위 순서**. 주요 기능이 가장 중요하며, ProWin은 **1. 자동화(요구사항 자동 추출) → 2. 자산화(자산 라이브러리, 유사 사례 추천) → 3. 주요 기능 품질(합본·미리보기) → 4. 그 외** 순이다.

## 장표 반영 기준 (최신)

- 제출 덱은 **20장**이다. 구성은 개요(성과 요약, 소개, 배경, 목표, 기대효과) → 업무 흐름 → **AI 설계 3장** → 핵심 기능 4종 → 부가 기능 2장 → 기술 구성 → 고도화 계획이다.
- **요구사항·목차 초안 자동 생성**(`docs/1117/ProWin_RFP_LLM_초안생성_계획.md`)과 **유사 사례 추천(RAG)**(`docs/1117/ProWin_개선계획.md`)은 **설계안으로 제출**한다. 구현은 고도화 계획에 "설계한 3종을 구현"으로 기술한다. 소스에는 LLM·RAG 코드가 아직 없으므로 장표는 "구현"이 아니라 "설계"로 표기한다.
- 설계 ① 초안 생성(AI) / 설계 ② 요구사항·목차·장표 연결(AI) / 설계 ③ 유사 사례 추천, RAG 저장소(AI)로 장표를 나눴다. 핵심 기능 1/4(RFP · 요구사항 관리) 장표에는 AI 태그를 붙이고, 요구사항 목록과 유사 사례 추천(예시 화면)을 확대해 보여 준다.
- 우측 상단 태그, 처리시간 추정, 일정, 품질 목표 수치는 장표에 싣지 않았다.
- `shots/rfp.png`는 우측 "유사 사례 추천" 카드의 "Step 2" 문구만 지운 것이다. 자산 라이브러리 타일은 해당 문구가 보이지 않는 영역으로 잘라 썼다.

### 제출 전 구현·확인 필요 목록 (2026-11-18 기준, `main`의 구현 반영)

구현된 범위와 설계 범위는 아래와 같이 장표에 구분해 쓴다. 구현이 장표 문구에 못 미치면 장표 문구를 낮춘다.

| 기능 | 구현 | 설계(고도화) | 장표 |
|------|------|--------------|------|
| 요구사항 후보 추출 | 규칙 기반(요구사항 총괄표 파싱, 번호 패턴) | 로컬 LLM 보완, 2차 검증, 목차 초안(설계 ①) | 9, 12, 19장 |
| 요구사항·목차·장표 연결 | 요구사항, 목차 기본 연결 | 장표 매핑, 조견표 쪽수 자동 채움, 미답변 감지(설계 ②) | 10, 19장 |
| 유사 사례 | 슬라이드 적재, 키워드·메타 검색(SQL LIKE) | 의미 검색, 사례 추천, 비밀 등급(설계 ③) | 11, 16, 19장 |

| # | 확인 항목 | 필요한 조치 |
|---|-----------|-------------|
| 1 | 합본 서식 보존(4, 15, 18장 "서식 보존 스냅샷") | 한화시스템 템플릿 PPT로 합본 시험 후 서식이 보존되는지 확인 |
| 2 | 합본 "불변 스냅샷"(4, 15장) | 수정·삭제 API 부재 외에 서버 차원의 강제 장치 확인, 없으면 문구 낮춤 |
| 3 | 제목 추출(제목칸, 그룹, 표 텍스트) | 실제 제안서 PPT 여러 건으로 추출 결과 확인 |
| 4 | 12장 화면 | 실제 화면(`shots/rfp.png`)과 확대 영역 일치 확인. 유사 사례 추천 합성 화면은 사용하지 않음 |
| 5 | "RAG" 표현(11, 19장) | 구현 시 용어 확정(벡터 검색 저장소 / RAG) |
| 6 | 설계 장표(9, 10, 11장) | 구현한 것은 규칙 기반 추출과 키워드 검색뿐이므로 LLM 추출, 의미 검색 기능이 구현된 것처럼 읽히지 않게 유지 |

이번 최신화에서 바꾼 장표 사항: 12장(RFP · 요구사항)에 유사 사례 추천 확대 카드를 넣고 앞 장 참조 문구 삭제, 4장 카드 순서(표준 절차 → 자산 라이브러리 → 버전관리)와 하단 문구, 6장 라벨 "실현 방안", 19장에서 "제안서 목차 자동 인식" 삭제(구현 완료로 처리)와 AI 태그 삭제.

### 제출 전 정리 필요 (설계안 간 불일치)

| 항목 | RAG 계획서 | 이 문서 2장 | RFP LLM 설계서 |
|------|------------|-------------|----------------|
| 구현 방식 | Python 별도 서버(FastAPI, ChromaDB), `prowin-simple` 기준 | SQLite FTS5 → sqlite-vec, 서버 내부 임베딩 | Java 단일 서버(Spring Boot) |
| LLM 사용 | OpenAI·Claude API 옵션 | 사내 모델 | 로컬 Ollama(Qwen3) |
| 상태·API | – | 1장: `candidate`, `/rfp/extract` | `draft`, `/rfp/drafts` |

- 장표는 "로컬 LLM, 서버 내 연동"으로 통일했다. 외부 API 옵션과 별도 Python 서버 안은 싣지 않았다. 개발 쪽에서 하나로 정리해 주면 장표와 맞는다.
- 1장의 방식은 하이브리드(C)로, LLM은 로컬로 확정된 것으로 본다(1-7 결정사항 중 LLM 범위는 해소).
- RAG 계획서는 `prowin-simple`(정적 JS) 기준이라 현재 `ProWin/backend` 구조에 맞게 다시 써야 한다.

| 순위 | 장 | 항목 | 구분 | 우선순위 | 현재 상태 |
|------|----|------|------|----------|-----------|
| 1 | 1장 | **요구사항 자동 추출** (자동화) | 고도화 | **P0** | 미착수(수동 등록만). 업무 흐름 STEP 01에 해당 |
| 2 | 2장 | **자산화**: 자산 라이브러리 적재·검색, 유사 사례 추천 | 고도화 | **P0** | 미착수(화면과 안내 문구만). 업무 흐름 STEP 02에 해당 |
| 3 | 3장 3-B | **합본 품질(서식 보존)** | 보완 | **P0 (제출 전 확인)** | 슬라이드만 복사, 마스터·테마·크기 소실. 장표의 "합본 자동 생성"과 직결 |
| 4 | 3장 3-A | 슬라이드 뷰어, 글꼴, 캐시 | 보완 | P1 | 작은 썸네일만 제공, 기호 글꼴 깨짐 |
| 5 | 3장 3-C | 내용 추출 정확도 | 보완 | P1 | 제목칸 미구분, 그룹·표 미처리. **자산화의 선행 조건** |
| 6 | 4장 | 그 외 소스 기준 보완 (파일명 검증, 인증, 테스트 등) | 보완 | P0~P2 | 4-1 표 |

우선순위: P0 = 제출·시연 전 또는 최우선 착수, P1 = 고도화 착수 전, P2 = 고도화와 함께.
- 합본은 3순위이지만 성과 장표가 "합본 자동 생성"을 말하므로 **제출 전에 먼저 확인**한다.
- 자산화(2장)는 3장의 내용 추출 정확도(3-C), 미리보기 이미지 생성(3-A)이 선행되어야 한다.

## 1. 자동화: 요구사항 자동 추출 (P0, 최우선 고도화)

### 1-1. 목표와 원칙
- RFP를 업로드하면 **요구사항 후보 목록**(코드, 제목, 설명, 출처 페이지)을 만들어 RFP / 요구사항 화면에 채운다.
- ReqSync와 같은 원칙을 따른다: **자동화는 후보 추출까지, 확정은 사람(PM·사업관리)**. 후보는 `candidate` 상태이고, 담당자가 수정·삭제·확정해야 기존 요구사항 목록에 반영된다.

### 1-2. 입력과 출력
| 구분 | 내용 |
|------|------|
| 입력 | RFP 파일(PDF, DOCX, 필요 시 HWP). 이미 `rfp_document` 에 파일명·페이지수·수령일을 저장하고 있음 |
| 출력 | `rfp_requirement` 후보 행: `code`, `title`, `description`, `source_page`, `confidence`, `status(candidate/confirmed/rejected)` |

### 1-3. 접근 방식 비교

| 방식 | 설명 | 장점 | 단점 |
|------|------|------|------|
| A. 규칙 기반 | RFP의 `요구사항 총괄표`에서 고유번호·명칭·설명 열을 표 파싱하거나 번호 패턴(예: `SFR-001`, `RF_XXX_001`)으로 분리 | 빠름, 외부 의존 없음, 재현 가능 | 표 형식이 다르면 실패, 본문에 흩어진 요구사항은 놓침 |
| B. LLM 기반 | 문서를 청크로 나누고 청크마다 요구사항을 JSON으로 추출, 중복 병합 | 형식 다양성에 강함 | 사내 모델 필요, 비용·시간, 환각 가능성 |
| **C. 하이브리드(권장)** | A로 표·번호 패턴을 먼저 추출하고, 남은 본문만 B로 보완. 결과를 합쳐 중복 제거 | 정확도와 범위의 균형 | 구현이 가장 큼 |

### 1-4. 처리 흐름(권장안)
1. 파일 → 텍스트·표 추출(PDF: Apache PDFBox, DOCX: POI XWPF. HWP는 변환 또는 별도 라이브러리). 페이지 번호 보존.
2. 요구사항 표 탐지 → 열 매핑(고유번호, 명칭, 설명) → 후보 생성(방식 A).
3. 표에 없는 본문은 "시스템은 ~해야 한다", "~ 제공", "~ 지원" 같은 요구 문형을 기준으로 청크를 고르고 LLM으로 후보 보완(방식 B).
4. 중복·유사 후보 병합, 신뢰도 점수 부여, `candidate` 로 저장.
5. 화면: 좌측 RFP 원문 페이지, 우측 후보 목록. 후보를 선택하면 원문 하이라이트, 수정·삭제·확정. 확정 시 기존 요구사항 목록에 반영하고 이력 기록.

### 1-5. API 초안
- `POST /api/projects/{id}/rfp/extract` → 작업 시작(비동기, 작업 ID 반환)
- `GET /api/projects/{id}/rfp/extract/{jobId}` → 진행 상태, 후보 개수
- `GET /api/projects/{id}/rfp/candidates` → 후보 목록
- `POST /api/projects/{id}/rfp/candidates/{cid}/confirm` · `reject` · `PUT` (수정)

### 1-6. 평가와 수용 기준
- **정답셋**: 과거 RFP 3~5건에서 PM이 확정한 요구사항 목록을 정답으로 사용.
- **지표**: 재현율(정답 중 찾은 비율), 정밀도(후보 중 맞는 비율), 원문 위치 일치율. 목표 수치는 정답셋 확보 후 합의한다.
- **PoC 범위 제안**: 요구사항 총괄표가 있는 RFP로 방식 A만 먼저 구현·측정하고, 부족분을 B로 보완.

### 1-7. 결정이 필요한 사항
- LLM 사용 가능 범위(사내 모델, 외부 API 허용 여부). 외부 API 불가이면 방식 A 중심으로 설계.
- RFP 파일 형식(HWP 포함 여부), 한 건당 최대 페이지.
- 고객 자료의 외부 전송 금지 정책 확인.

## 2. 자산화: 자산 라이브러리와 유사 사례 추천 (P0)

> 구현이 어려운 경우를 대비해 **방법론과 단계별 대안**을 함께 정리한다.

### 2-1. 목표
요구사항(제목+설명)을 입력하면 **과거 제안서에서 유사한 슬라이드**를 찾아 작업자에게 제시한다. 자산 라이브러리의 `의미 기반 검색(Step 2)` 이 이 기능의 기반이다.

### 2-2. 선행 조건: 자산 적재
- 과거 제안서 PPTX를 **슬라이드 단위로 분해**하여 저장한다: 제목, 본문 텍스트, 썸네일 PNG, 원본 파일·슬라이드 번호.
- 메타데이터를 함께 받는다: 사업명, 고객 부문, 연도, 수주 여부, 작성자, 비밀 등급, 키워드 태그.
- 3-C(추출 정확도), 3-A(미리보기 이미지 생성)가 선행되어야 한다. 이 둘이 곧 적재 파이프라인이다.

### 2-3. 검색 단계 (낮은 비용부터 순서대로)

| 단계 | 방식 | 구현 | 외부 의존 | 기대 수준 |
|------|------|------|-----------|-----------|
| P0 | **메타·키워드 검색** | SQLite FTS5(한글은 `trigram` 토크나이저) + 메타 필터(연도, 부문, 수주 여부) | 없음 | 용어가 겹치는 사례는 찾음 |
| P1 | **의미 검색(임베딩)** | 한국어 임베딩 모델(예: multilingual-e5, bge-m3 계열)을 서버 내부에서 실행, 슬라이드 텍스트를 벡터화해 저장. SQLite 벡터 확장(sqlite-vec) 또는 별도 벡터 인덱스. 질의도 같은 모델로 벡터화 후 코사인 유사도 | 모델 파일(사내 반입 필요) | 표현이 달라도 의미가 비슷한 사례를 찾음 |
| P2 | **결합과 재정렬** | P0(BM25)와 P1(벡터) 결과를 점수 결합(RRF), 필요 시 LLM으로 "이 요구사항에 이 슬라이드가 맞는가" 재판정과 한 줄 요약 | 사내 LLM(선택) | 상위 결과의 정확도 향상 |

### 2-4. 질의와 결과 화면
- **질의 생성**: 요구사항 `title + description` 을 그대로 쓰거나, P2에서 LLM이 핵심 키워드를 뽑아 질의를 보강.
- **결과**: 상위 N개 슬라이드의 썸네일, 출처(제안서명, 연도), 수주 여부, 유사도. 작업자가 `참고 슬라이드 열기`, `관련 요구사항에 연결` 할 수 있다.
- **피드백**: 유용함/아님 버튼으로 로그를 쌓아 가중치와 평가 데이터로 활용.

### 2-5. 평가
- **정답셋**: 과거 요구사항 20~30건에 대해 담당자가 "참고했던 과거 슬라이드"를 지정.
- **지표**: Recall@5(상위 5개 안에 정답 포함 비율), 담당자 만족도(유용 클릭 비율).
- P0만으로도 효과가 있는지 먼저 측정하고, 개선 폭이 크지 않으면 P1 투입을 보류한다.

### 2-6. 반드시 확인할 위험
- **비밀 유지**: 고객사가 다른 제안서의 내용이 노출될 수 있다. 제안별·비밀 등급별 접근 제어와 마스킹 정책이 필요하다. 이 정책이 없으면 검색 범위를 "자사 공개 가능 자산"으로 제한한다.
- **데이터 품질**: 슬라이드 텍스트가 거의 없는 이미지형 슬라이드는 검색되지 않는다(3-C의 그룹·표 처리, 필요 시 OCR).
- **모델 반입**: 임베딩 모델 파일을 사내망에 반입할 수 있는지 확인한다.

### 2-7. 구현하지 못하는 경우의 대안
| 대안 | 내용 |
|------|------|
| 큐레이션 | 담당자가 우수 사례 슬라이드를 직접 `태그`(요구사항 유형, 키워드)와 함께 등록하고, 태그 필터로 찾는다 |
| 메타 필터 + 키워드(P0만) | 연도·부문·수주 여부 필터와 키워드 검색만 제공 |
| 요구사항-사례 수동 매핑 | 요구사항 화면에서 "과거 참고 슬라이드"를 사람이 연결하고 이후 제안에서 재사용 |

### 2-8. 결정이 필요한 사항
- 과거 제안서를 자산 라이브러리에 적재해도 되는 범위(고객·비밀 등급).
- 임베딩 모델과 LLM을 사내에서 사용할 수 있는지, 서버 사양(CPU/GPU).

## 3. 주요 기능 품질: PPT 처리(미리보기·합본) (P0~P1)

### 3-1. 검증 결과 (현재 수준)

| 항목 | 결과 | 비고 |
|------|------|------|
| 업로드 → 커밋(이력) 저장 | 정상 | 한글 파일명은 서버 UTF-8 설정 필요(4장 #2) |
| 제목·핵심 내용 추출 → 검토 노드, 목차 장수 갱신 | 정상 | 샘플 PPT 기준. 3-C의 제약 있음 |
| 미리보기(POI `slide.draw`) | 부분 정상 | 템플릿 29장 중 시험한 장에서 도형, 색, 표, 텍스트 배치는 원본과 거의 동일 |
| 합본(`PptxMerger`) | **서식 손실** | 3-B 참고 |

### 3-A. 미리보기 보완

**현상**
- 검토 화면에 약 250px 폭 썸네일 3개만 보여 글자를 읽을 수 없다(`PREVIEW_WIDTH = 960` 으로 그린 이미지를 작게 줄여 표시).
- 글머리 기호(Wingdings 등)가 `♣` 로 깨진다. 지정 글꼴(나눔바른고딕 등)이 서버에 없으면 대체 글꼴로 그려져 줄바꿈이 달라진다.
- 요청마다 PPTX를 열어 다시 그린다(캐시 없음).
- 시험하지 못한 위험: 차트, SmartArt, EMF/WMF 벡터 이미지, 애니메이션 효과는 POI에서 누락·왜곡될 수 있다.

**보완 요청**
1. **슬라이드 뷰어**: 썸네일 클릭 시 모달 또는 우측 패널에 큰 이미지(1200~1600px 폭), 이전/다음 이동, 슬라이드 번호, 키보드 방향키.
2. **서버 글꼴 설치**: 나눔바른고딕(및 한화시스템 사용 글꼴), 기호 글꼴 대체 매핑(Wingdings → 일반 글머리 기호).
3. **캐시**: 커밋 시점에 슬라이드별 PNG를 파일로 저장하고 재사용. 합본 스냅샷도 같은 방식.
4. **고충실도 옵션(필요 시)**: POI로 부족하면 LibreOffice headless로 `PPTX → PDF → PNG` 변환을 병행. 아래 표로 선택한다.

| 방식 | 장점 | 단점 | 권장 |
|------|------|------|------|
| POI 직접 렌더링(현행) | 의존성 없음, 빠름 | 차트·SmartArt·기호 글꼴 한계 | 기본값 |
| LibreOffice 변환 | 렌더링 정확도 높음 | 서버 설치, 변환 시간, 글꼴 의존 | POI 품질 미달 시 보조 |
| 외부 뷰어(Office Online 등) | 원본과 동일 | 사내망·보안 제약, 외부 의존 | 비권장 |

**수용 기준**: 템플릿 PPT 29장을 올려 PowerPoint 화면과 나란히 비교했을 때 글자가 읽히고 레이아웃이 어긋나지 않는다. 차트·SmartArt가 있는 슬라이드는 누락 시 "미리보기 제한" 안내를 표시한다.

### 3-B. 합본 품질 (P0)

**원인**: `PptxMerger.merge` 가 `new XMLSlideShow()` 로 빈 문서를 만들고 `createSlide().importContent(slide)` 로 슬라이드 내용만 복사한다. 원본의 슬라이드 마스터, 레이아웃, 테마, 배경, 페이지 크기는 가져오지 않는다.

**재현 결과(템플릿 PPT 합본)**
- 페이지 크기가 4:3(720×540pt)로 고정되어 A4·16:9 슬라이드의 오른쪽이 잘린다.
- 표지의 주황 배경 등 마스터·레이아웃 배경이 사라진다. 모든 슬라이드의 레이아웃이 `Blank` 로 바뀐다.
- 템플릿 슬라이드 일부에서 텍스트 런(`a:r`)에 `a:t` 가 없는 XML이 생성된다. PowerPoint에서 열 때 복구 메시지가 뜰 수 있다(PowerPoint로는 확인하지 못함, python-pptx로 읽을 때 오류).
- 깨진 소스 파일은 예외를 무시하고 건너뛴다. 합본에서 슬라이드가 조용히 빠져도 사용자는 알 수 없다.
- 단순 서식의 샘플 PPT 15장은 문제없이 합쳐진다.

**개선안(우선 검토 순서)**
1. **기준 문서 방식**: 첫 소스(또는 지정한 제안 템플릿 PPT)를 열어 마스터·테마·페이지 크기를 그대로 쓰고, 나머지 슬라이드를 추가한다. 슬라이드마다 원본 레이아웃을 대상 문서의 레이아웃으로 매핑한다.
2. 소스별 마스터가 다르면 마스터·레이아웃·테마를 대상 문서로 함께 복제한다(POI `XSLFSlideMaster` 복제, 관계(rels)와 미디어 파트 포함). 구현 난이도가 높다.
3. 대안: LibreOffice(UNO) 또는 다른 변환 엔진으로 병합. 서식 보존이 가장 좋지만 서버 의존이 커진다.
4. 병합 전에 소스 파일 검증(열기 가능 여부, 슬라이드 크기 일치 여부)을 하고, 건너뛴 파일은 **응답과 화면에 목록으로 알린다**.

**수용 기준**
- 서로 다른 서식의 PPT 3종 이상(표 포함, 이미지 포함, 그룹 도형 포함)을 합본해 PowerPoint에서 오류·복구 메시지 없이 열린다.
- 합본 슬라이드 수·순서가 목차 순서와 일치하고, 페이지 크기와 배경이 소스와 같다.
- 건너뛴 파일이 있으면 화면에 사유와 함께 표시된다.
- 자동 테스트: 샘플 PPT 3종으로 병합 후 슬라이드 수, 크기, 레이아웃 이름을 검증.

### 3-C. 내용 추출 정확도 (P1)

**현상(소스 `PptxExtractor.extract`)**
- 제목은 "슬라이드에서 처음 만난 텍스트 도형의 첫 줄"이다. 제목 칸(placeholder)을 구분하지 않아 사용자 가이드의 "제목칸에 입력하세요" 규칙과 코드가 다르다.
- 그룹 도형(`XSLFGroupShape`), 표(`XSLFTable`) 안의 텍스트는 순회하지 않아 누락된다. 템플릿 기반 슬라이드는 대부분 그룹을 쓴다.
- 핵심 내용은 슬라이드 전체에서 최대 20줄(`BULLET_LIMIT`)이고 슬라이드 구분 없이 이어 붙인다.
- 발표자 노트, 이미지 속 글자는 다루지 않는다.

**보완 요청**: 제목 placeholder(`XSLFTextShape.getTextType() == TITLE`)를 우선하고, 없으면 상단 위치 기준 첫 도형. 그룹·표 재귀 순회. 슬라이드별로 핵심 내용을 구분해 저장. 추출 결과가 비면 사용자에게 "내용을 읽지 못했다"는 사유를 표시.

## 5. 권장 진행 순서

1. **자동화(1장)**: 요구사항 자동 추출을 방식 A(요구사항 총괄표 파싱)로 먼저 구현하고 정답셋으로 측정, 부족분은 방식 B(LLM)로 보완. 확정은 사람이 한다
2. **자산화(2장)**: 3-C(추출 정확도)와 3-A(미리보기 이미지)를 선행하여 슬라이드 단위 적재 → 키워드·메타 검색(P0 단계) → 효과 측정 후 의미 검색(P1 단계) 판단
3. **주요 기능 품질(3장)**: 합본 서식 보존(3-B)을 제출 전에 먼저 확인, 이어서 뷰어·글꼴·캐시(3-A)
4. **그 외(4장)**: 파일명 검증·UTF-8(4-1 #1, #2), 자동 테스트(4-1 #11), 인증·예외·트랜잭션(4-1 #3~5), 성능 측정(#13), 나머지 화면 DB 연동

```bash
  java -Dfile.encoding=UTF-8 -Dsun.jnu.encoding=UTF-8 -jar target/backend-0.0.1-SNAPSHOT.jar
```
1. 샘플 PPT 5개를 `POST /api/projects/P-001/versions/commits`(multipart: file, message, who, tocRowId)로 업로드.
2. `GET .../commits/{hash}/slides/{index}` 로 미리보기 PNG 확인.
3. `POST .../versions/snapshot` 으로 합본 생성, `GET .../commits/{hash}/download` 로 내려받아 PowerPoint와 python-pptx로 열어 슬라이드 수·크기·레이아웃 확인.
4. 한화시스템 템플릿 PPT(29장)를 같은 방식으로 업로드해 미리보기와 합본의 서식 손실을 확인.
